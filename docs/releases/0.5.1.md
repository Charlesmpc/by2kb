# by2kb 0.5.1 — readable missing-title fallback

Before summaries, the existing API or external Agent enrichment client generates
one concise title from transcript evidence when the source title is blank, a bare
BVID, or an exact generic placeholder (`Untitled`, `Unknown title`, `Video`,
`无标题`, etc.). Ordinary readable titles are never rewritten just to improve style.
There is one effective `source.title`, not an alternative display-title field.

## Provenance and artifacts

`title_source` is `original` or `generated`. Missing, null or whitespace-only legacy values
mean `original`; they do not exempt a BVID/blank title from checking. Generated
provenance is propagated into `source.json` (top-level and nested source metadata),
`transcript.json`, and Markdown frontmatter. The generated title is used for the
raw heading, raw/short/long filenames, summary metadata, prompts and chunk plans.
The raw transcript text itself is not changed. Existing unrelated source metadata
is retained. Summary bodies remain governed by the configured Skills.

Title generation requests use a bounded 12,000-character transcript excerpt. The
model must return JSON `{"title":"...","evidence":"exact transcript quote"}`,
with a plain title of 3–100 characters. Invalid JSON, placeholders, multiline or
oversized titles and non-matching evidence are rejected, not silently substituted.
An exact quote validates the evidence's presence, not semantic correctness of the
model's title; review generated titles where correctness is critical. The model
can abstain with `{"title":null,"evidence":""}`. Empty/very short or failed-quality
transcripts do not trigger title generation. There is no first-sentence truncation
fallback and no invented title when evidence is insufficient.

## External Agent compatibility

The staged `enrichment next` / `enrichment submit` schema remains version 1.
For missing titles, the first live operation asks for the title JSON; normal
chunk/reduce/summary operations follow with the resolved title. Invalid title
submissions are rejected before caching so the host can resubmit the same pending
operation. API enrichment uses exactly the same generation and validation path.

`enrichment claim` returns `title_required: true`, a title prompt, and empty `outputs`
with `pipeline: null` when a title operation must precede summary planning. Use
`enrichment next` and `enrichment submit` to finish such jobs. Legacy whole-summary
completion remains supported for readable titles; it cannot bypass a required
title operation. Existing hosts using the staged protocol need no schema change.

## Upgrade and raw-only behavior

Upgrade the package normally; do not reinitialize the home or database. Upgrading,
listing and duplicate ingestion never scan or rewrite archived jobs. Explicit
`--re-enrich` checks only the selected stored transcript and republishes coherent
raw/short/long artifacts after enrichment succeeds. Previous filenames for that
job are retired by the existing filesystem sink at publication, not at upgrade.

With enrichment disabled, raw-only ingestion remains raw-only: it does not need
an API key, a new provider or a host-model call. A missing title remains the source
placeholder/BVID until the user explicitly re-enriches with API or external Agent.
During pending Agent enrichment the initial raw artifact also retains that title;
the final artifact set is published only after the staged enrichment completes.

## Validation

Regression tests use local transcript fixtures and fake model responses. No live
ASR, browser, production pipx installation or private configuration is required.
